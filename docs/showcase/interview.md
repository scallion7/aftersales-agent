# 项目讲解与面试追问

[展示材料](README.md) · [项目卡](project-card.md) · [文档中心](../README.md) · [当前验收](../evaluation/acceptance.md)

下面的讲稿按当前实现组织。时间段用于控制篇幅，实际语速和演示耗时需自行排练。涉及个人职责时使用自己实际承担的表述，项目实现、历史验证结果与待完成工作保持各自口径。

## 3 分钟介绍稿

### 0:00–0:40 业务问题

这个项目是电商售后 Agent。以用户说“衣服尺寸不合适，想退货”为例，完整处理需要核对订单归属、查适用政策、补齐申请资料，再由用户确认具体操作，必要时转客服审批。我围绕这条流程组织系统，让每一步都有可查看的状态、证据和恢复路径。

### 0:40–1:15 系统结构

客户页面通过 FastAPI 提交持久化任务，独立 Worker 领取后运行 Agent。Agent 支持 ReAct、计划执行和多 Agent 路由，经过统一工具层查询订单、检索政策或提出业务操作。政策查询关联知识版本和原文引用，资料分轮保存到申请草稿。身份、权限、确认和业务状态由服务端校验，模型输出不能直接充当授权。

### 1:15–2:10 最重要的设计

最值得展开的是两类异常。第一类是授权变化，用户改诉求、审批内容变化或者客服接管时，原确认可能已经不适用，所以提案要绑定参数和业务版本，执行时再检查。第二类是结果未知，例如供应商已经受理退款但响应丢失。系统先保存稳定业务键，随后查原键并核对回执，保留待核对状态。Worker 的租约和 fence 控制本地提交资格，已经发出的外部请求仍需要业务对账。

### 2:10–3:00 验证与边界

项目已有回归、浏览器交互、双数据库迁移和故障演练。2026 年 11 月 13 日的本地验收是 500 项通过、没有跳过，app 语句覆盖率 82%。评测发布流程会检查实际回答、关键事实、引用和原始报告，一次计划执行策略输出无关问候时，门禁确实阻止了发布。当前 27 格结果使用受控模型，证明的是已覆盖的工程流程。原 32 题人工审核还未完成，真实模型评测等审核完成后再做。现场可以演示查询、申请、确认和人工接管，也可以深入讲一次退款异常恢复。

依据见[项目卡](project-card.md)和[2026-11-13 原始检查清单](../evidence/release-workflow-20261113/checks.json)。现场操作见[演示材料](demo.md)。

## 10 分钟深讲稿

### 0:00–1:00 用一个订单说明目标

先展示客户工作区中的合成订单，再描述“查政策—补资料—确认—办理”的业务线。一个有效的售后系统需要知道谁在操作、针对哪个订单、当前材料是什么，以及失败以后怎样继续。项目把这些业务事实放到服务端的持久化状态中，Agent 负责把自然语言需求转成可检查的步骤。

补充说明这套演示使用合成业务和受控模型，服务端、HTTP、Worker 与数据库实际运行。这样可以稳定复现界面与协议，同时把真实模型效果留给独立评测。

### 1:00–2:20 展开一次请求的路径

打开架构图，从客户页面指向 `/v1/runs`。提交任务后，SQL 保存任务及事件，Worker 领取租约，加载该会话固定的运行配置，再进入 Agent。Agent 调用模型或工具时记录调用账本，通过统一工具层应用权限、预算与确认检查。最终状态和事件供页面查询或流式展示。

解释为什么保留这个边界。HTTP 请求可能断开，模型调用可能慢，Worker 也可能退出。任务状态独立于浏览器连接后，服务端能判断它是排队、执行、已完成还是需要人工核对。兼容同步 chat 入口仍存在，其恢复保证与持久化任务路径分别说明。

此处可打开[任务仓储](../../app/repositories/runs.py)的 `submit`、`claim`、`change`，说明输入持久化、领取与提交检查各自发生在哪里。

### 2:20–3:50 说明政策证据与多轮申请

在客户页面提出政策问题，展示文档版本和 chunk 定位。政策适用性取决于日期、地域、渠道、商品等信息，条件来源要能追溯到用户明确输入或所属订单。换单时不能沿用另一订单的条件。检索组合 BM25、余弦相似度和 RRF，当前演示向量为本地哈希表示，重排采用词法规则。

然后展示分轮保存订单和原因。草稿有修订号，更新时检查预期版本，避免两个客户端覆盖彼此资料。生成提案后修改诉求会使旧确认失效。解释工单创建与退款执行的区别，确认创建工单并不自动授权后续退款。

可以追踪[申请服务](../../app/platform/after_sale_intake.py)和[政策上下文回归](../../tests/test_policy_context.py)，分别展示业务资料与检索条件的来源隔离。

### 3:50–5:30 讲清授权和人工接管

展示待确认卡中的订单、原因和操作。服务端 action 绑定用户、会话、工具、参数哈希、业务版本及有效期。用户确认后，执行领取还要再次检查这些条件。这样用户确认 A 操作以后，模型或另一客户端不能把参数改成 B 再沿用原授权。模型在文本或工具参数中声称“用户已确认”也无法完成这一步。

转到客服工作台说明接管。系统记录会话所有权版本，在每次调用登记和最终回复提交时检查。客服接管后再释放也会改变版本，旧任务无法因为当前状态又变回 agent 而继续。已登记的在途请求仍可能产生结果，因此接管不被解释成撤销远端操作。交接中的用户输入、事件和终态同事务提交，崩溃后可以恢复且不重复追加消息。

展示[确认回归](../../tests/test_trusted_actions.py)中的参数变更案例，以及[交接回归](../../tests/test_handoff_execution.py)中接管后阻止下一次调用的案例。

### 5:30–7:20 用退款响应丢失解释恢复

设想供应商已受理退款，网络却在返回回执前断开。仅凭超时无法判断资金动作是否发生，因此不能换一个请求键重新提交。系统首次执行先持久化业务键 `after_sale.execute:<case_id>`，把后续恢复关联到同一操作。查单结果必须匹配订单、用户、金额、退款编号和终态，只有“成功”文字的响应不足以结案。

Worker 的租约处理另一个问题。新 Worker 接管时递增 fence，旧 Worker 恢复后不能再提交过期的本地状态。但 fence 无法撤回已经发出的 HTTP 请求，所以还需要业务幂等和对账。HTTP 商务路径通过事务 Outbox 保存待发送意图，Inbox 去重回执；普通外部适配器采用对应查单协议。两种路径的恢复能力都依赖供应商实际支持的契约。

打开[外部退款回归](../../tests/test_external_refund_recovery.py)中超时、进程重启和并发查单的用例，展示如何断言没有再次提交。管理员处理 run 时仍需核对关联证据，`resolved` 表示原流程已核对关闭，并不承诺退款一定成功。

### 7:20–9:00 展示评测如何阻止错误发布

模型或 Prompt 更新后，先固定配置和知识快照，再在隔离临时库中运行评测，避免评测修改源业务数据。任务级评测检查真实 HTTP、工具调用与 SQL 终态；政策回答评测另外检查实际回复中的关键事实、原文引用和转人工原因。任务 completed 只能说明执行结束，回答是否正确需要后者判断。

一次已有验收中，计划执行策略对五个可回答问题返回通用问候，虽然请求能够结束，评分仍然拒绝了发布。修复受控模型读取计划步骤的检索结果后，三个策略各通过九题。报告摘要关联有 SHA-256 的压缩原件，导入发布时复算评分与完整性，因此不能手动把摘要改成通过就绕过检查。

配置发布还固定风险阈值。否则两台 Worker 环境配置不同，即使会话名称相同，也可能做出不同审批决定。完整实现及负向测试见[发布代码](../../app/platform/releases.py)、[评测发布回归](../../tests/test_agent_quality_cli.py)和[风险阈值回归](../../tests/test_pinned_risk_limits.py)。

### 9:00–10:00 用证据回答完成度

打开验收页，指出 2026-11-13 的本地 500 项通过与 82% app 覆盖率，再打开固定提交的九个 CI 作业。解释浏览器专项、数据库迁移、Compose 部署和故障演练验证的对象。受控模型的用量是模拟 usage，短时本地负载也不能直接换算生产容量。

最后说明下一项质量工作是完成 32 题人工审核，随后运行冻结保留集和真实模型评测。目前展示内容集中在能够复现的业务与工程行为。根据面试岗位，可以继续展开策略调度、RAG 条件处理、SQL 幂等或故障恢复中的一个主题。

## 常见追问与回答要点

### 1. 项目解决的最核心问题是什么？

让自然语言交互能够进入可核验、可恢复的业务流程。回答“可以退货”只解决咨询；真正办理还需要订单归属、材料、确认、审批和执行结果。项目把这些事实持久化，并对未知结果保留核对路径。现场用“用户修改诉求后旧确认失效”说明设计价值，比罗列组件更容易理解。[业务与确认边界](../engineering/reliable-execution.md)

### 2. 为什么同时支持 ReAct、Plan-and-Execute 和多 Agent？

ReAct 适合按观察结果逐步调用工具；计划执行显式保存步骤、依赖和执行状态；多 Agent 路由按职责组织任务。它们共同使用业务执行边界，策略选择不会绕过确认和权限。当前三种策略的受控矩阵验证工程兼容性，不能据此排序真实效果或成本。要比较效果，需要同一冻结数据、真实模型、预算和重复实验。[策略实现](../../app/agent/strategies/) · [多 Agent 实现](../../app/multi_agent/) · [受控矩阵](../evaluation/offline-review.md)

### 3. 为什么 Prompt 中写“必须确认”还不够？

Prompt 是模型输入，不能证明用户授权。服务端保存 action 并绑定身份、会话、参数、业务版本和有效期，确认及执行都核对这些字段。攻击文本或模型参数中的 `user_confirmed=true` 不构成有效确认。测试同时覆盖模型自报确认、其他用户确认、参数改变和过期授权。[统一执行层](../../app/services/tool_execution.py) · [可信确认测试](../../tests/test_trusted_actions.py)

### 4. 幂等键相同就能保证不重复退款吗？

还需要请求范围、数据库约束、持久化回执及供应商的幂等和查单契约。项目先保存稳定业务键，提交后超时进入待核对状态；恢复只查原键，校验终态回执后收敛。不同键表达相同意图也可能造成重复，因此不能为绕过未知结果随意换键。外部供应商不满足契约时，不能承诺资金动作恰好一次。[退款契约](../../app/services/refund_contracts.py) · [恢复回归](../../tests/test_external_refund_recovery.py)

### 5. 租约和 fencing 分别解决什么问题？

租约让任务在 Worker 不再续持时具备接管条件。fence 是领取版本，提交时同时核对任务、所有者、版本和租约，阻止旧 Worker 恢复后覆盖新状态。它约束本地受检查的提交，已经发出的外部请求仍可能执行，需要幂等与对账处理。[任务仓储](../../app/repositories/runs.py) · [异步任务回归](../../tests/test_async_runs.py)

### 6. Outbox/Inbox 是否实现了端到端 exactly-once？

Outbox 将本地业务变更和发送意图放入事务，发送进程可以重试，因此消息仍可能重复投递。Inbox 根据回执身份去重，业务端还必须检查稳定业务键。最终效果取决于远端的幂等、查单和回执契约。本项目描述的是这些条件下的幂等效果及对账恢复。[投递实现](../../app/services/refund_delivery.py) · [投递回归](../../tests/test_refund_delivery.py)

### 7. 人工接管能立即终止所有 Agent 动作吗？

接管会改变所有权版本，阻止旧任务登记后续新调用及直接发布自动回复。已经登记的在途调用仍可能完成，执行中的 action 也有专门的冲突处理。接管后再释放不能恢复旧授权。交接任务完成只代表已转交，业务结果未知时仍需核对。[交接机制](../engineering/human-handoff.md) · [竞争场景测试](../../tests/test_handoff_execution.py)

### 8. 同名用户、令牌续签和浏览器重试怎么处理？

服务端 OIDC 身份由精确 issuer/sub 派生，显示名变化不改变权限，不同主体同名也不会共享身份。浏览器未决请求使用服务端认证后的稳定存储范围，令牌续签后可以复用原键，换主体则隔离。旧用户名归属的数据需显式核验映射。[身份实现](../../app/security/identities.py) · [身份回归](../../tests/test_oidc_identity.py) · [续签与丢回执测试](../../tests/test_browser_retries.py)

### 9. RAG 如何处理政策矛盾与条件缺失？

先过滤日期、政策类型和适用范围，再排序检索；对最终命中的政策键回看适用快照中的相关条款，安全判断不局限于展示的前 K 条。缺少必要条件则澄清，同键适用条款的结构化 decision 冲突则转人工。该机制依赖元数据，不自动解决任意自然语言语义矛盾。[检索实现](../../app/platform/retrieval.py) · [知识平台测试](../../tests/test_knowledge_platform.py)

### 10. 混合检索和重排带来了多少提升？

当前没有足够证据给出真实语义质量提升。演示使用本地哈希向量和词法重排，已有历史诊断使用尚未真实审核的标签。可以解释 BM25、余弦和 RRF 的实现及候选过滤，也可以展示索引一致性测试；效果增益需要人工金标准、冻结保留集和同条件对比。[检索实验口径](../evaluation/retrieval-experiments.md) · [诊断实现](../../app/platform/retrieval_diagnostics.py)

### 11. 为什么有“任务完成”还要独立评分？

任务结束不代表回答相关、事实正确或引用有效。任务契约检查工具轨迹和数据库终态，政策评分再逐格检查关键事实、实际回复、精确引用和转人工原因。当前原文规则较保守，自由改写可能被拒绝，不能把它称为完整语义蕴含判断。[评分实现](../../app/platform/agent_quality.py) · [事实和引用负向回归](../../tests/test_agent_quality_cli.py)

### 12. 怎样防止评测报告被篡改或评测污染业务库？

指定配置评测时只读复制其知识快照，测试会话、调用账本和业务数据进入临时库。摘要只指向同目录的压缩原件，读取时验证 SHA-256 和摘要一致性；发布再检查完整矩阵、逐格评分、manifest 与实际知识快照。哈希保证已记录原件的一致性，生产放行另需真实模型和真实审核证据。[隔离工作区](../../app/platform/evaluation_workspace.py) · [原件校验](../../app/platform/evaluation_artifacts.py) · [端到端回归](../../tests/test_agent_quality_cli.py)

### 13. 为什么审批阈值要放进配置版本？

同一旧会话可能由不同 Worker 恢复，如果阈值随进程环境变化，审批结果会漂移。新草稿固定金额阈值并参与 manifest 哈希，恢复时按该版本重建规则。历史版本缺少阈值时无法证明原值，新增申请保守进入人工审批，不能猜一个默认值声称与历史一致。[版本实现](../../app/platform/releases.py) · [阈值回归](../../tests/test_pinned_risk_limits.py)

### 14. 为什么使用 SQL 任务队列？扩容时如何考虑？

当前任务、事件、调用与业务状态需要事务协调，SQL 让领取、条件更新和业务回执能够使用明确的一致性边界。它也带来轮询、锁竞争和连接数约束。已有短时负载只验证指定环境；若未来引入独立消息队列，需要保留业务幂等、任务版本与重投递处理，并重新测量吞吐、延迟和恢复能力。[任务仓储](../../app/repositories/runs.py) · [负载验收](../operations/sustained-load.md)

### 15. 500 项测试和 82% 覆盖率证明了什么？

它们来自 2026-11-13 的本地 Python 3.11 运行，启用了 Chromium，覆盖单元、集成及浏览器场景；82% 是 app 语句覆盖率，脚本与独立进程沿用配置排除。测试能证明对应断言在该环境成立，覆盖率能帮助找未执行路径，两者都不能证明零缺陷或真实模型效果。CI 对 Python 3.10–3.12、部署和数据库另做验证。[验收记录](../evaluation/acceptance.md) · [覆盖率配置](../../pyproject.toml)

### 16. 如何证明个人贡献，下一步准备做什么？

按“具体问题—实现位置—失败用例—验证结果”说明贡献，再展示提交和演进记录。当前可深入讲可信确认、恢复、检索条件或评测中的实际参与部分，不把依赖和通用方法写成个人原创。下一项效果工作是在真实人工审核完成后，按冻结协议测试保留集与真实模型，记录质量、延迟和费用；生产接入另需组织身份、订单及支付供应商联调。[工程演进](../CONTRIBUTIONS.md) · [后续验收条件](../evaluation/acceptance.md)

## 排练时的自查

每次选三个追问，先独立回答，再打开代码确认。答案至少包含一个具体输入、状态变化或故障窗口，以及一项对应断言。解释不清楚的部分回到[分层教学](../learning/README.md)完成实验；演示中出现异常则按[演示材料](demo.md)保留原状态和证据，不把未知结果口头解释为成功。
