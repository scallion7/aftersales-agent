## 哪些情况改变了处理结果

- **商品范围**。旧逻辑会漏掉条款明列的子类，也会把配件名里的“风衣”当成本体。现在按条款里写出的完整商品名、所属类目和列明的子类核对。指定了订单商品时，还要核对问句与订单是否一致。因而“风衣防尘罩退货”可以引用防尘罩条款，“风衣防尘罩换货”仍找不到依据。
- **付款条件**。旧逻辑偏重“已付／未付”，无法区分部分付款、待清算、撤回成功和结清到账。现在同时核对款项、当前状态、动作，以及条款指定的执行人、账户或页面。含有多个状态时，只有问题明确给出变化顺序、指向同一笔款项，才使用后来的状态。“等待清算”可以回答要等什么结果，不能据此承诺几点到账。
- **多轮追问**。旧会话只记得上一轮的证据状态，模型把检索词改短或沿用上轮检索词时，可能错引旧规则。现在根据本会话的用户原话补全省略的条件，用同一问题检索并复核最终引用。换商品、改办换货、剪掉吊牌或更正付款状态会触发重新核对。商品指代不明时请求澄清，转查订单后结束政策话题。

另用一段两轮订单对话复核。第一轮按旧订单取得了上海、门店、服饰三项信息。第二轮重载会话后，用户明确改查另一订单，受控模型仍传旧订单号。基线错误引用旧订单的七天退货政策。修复后要求确认当前订单，响应没有引用，也没有沿用旧订单条件。紧邻中文的订单号和仅说“另一笔订单”两种追问也得到相同修复。用户明确说“不是另一笔订单”时继续按当前订单作答。这个换单场景及其变体单独记录于 57 项之外。[两轮输入、订单来源与实际回复](../evidence/policy-transfer-20261118/order-change.json)

## 复现

在仓库根目录安装锁定依赖后执行下面的命令。前一条通过公开 HTTP 检索和真实 Agent 运行本轮用例，后两条分别复跑上轮 16 道开发题和 32 道补充题。

```bash
python -m unittest tests.test_policy_product_transfer tests.test_policy_payment_transitions tests.test_policy_followup_transfers tests.test_policy_transfer_controls
python -m app.scripts.compare_retrieval --output test-results/previous-development.json
python -m app.scripts.compare_retrieval --dataset docs/evidence/policy-paraphrases-20261118/challenge.json --output test-results/previous-challenge.json
```

历史 16 题和 32 题在两份检索配置、四种检索模式下均返回预期状态和文档。上轮 8 道口语补查在原配置的混合检索加重排模式下全部通过。[历史题与全量测试结果](../evidence/policy-transfer-20261118/verification.json)
